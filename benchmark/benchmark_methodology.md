# Методика измерения производительности

## 1. Назначение эксперимента

Эксперимент предназначен для сравнительной оценки времени выполнения типовых аналитических запросов при использовании четырех архитектур хранения пространственно-временных данных о посевных площадях:

- **модель I** — базовая реляционная структура без дополнительных индексов и предварительно рассчитанных аналитических структур;
- **модель II** — реляционная структура с GiST-индексом по геометрии и B-tree-индексами по атрибутам `season`, `crop` и их комбинации;
- **модель III** — реляционная структура с предварительно сформированными материализованными представлениями;
- **модель IV** — многомерная структура типа «звезда» с таблицей фактов и измерениями времени, культуры, муниципального образования и землепользователя.

Сравнение выполнялось на одном исходном наборе данных и при одинаковых параметрах СУБД.

Перед измерением производительности была проверена семантическая эквивалентность результатов соответствующих реализаций аналитических запросов.

## 5. Расчет площади

Во всех соответствующих сценариях площадь исходной геометрии рассчитывалась единообразно:

```sql
ST_Area(ST_Transform(geom, 3857)) / 10000.0
```

Результат выражался в гектарах.

Одинаковый способ расчета использовался для обеспечения сопоставимости результатов всех исследуемых архитектур.

---

## 6. Территориальное отнесение объектов

Для запросов, использующих муниципальные образования, применялось единое правило пространственного сопоставления.

Для каждого исходного объекта:

1. определялись муниципальные образования, пересекающие его геометрию;
2. для каждого пересечения рассчитывалось отношение площади пересечения к площади исходного объекта;
3. выбиралось муниципальное образование с максимальной долей пересечения;
4. объект относился к выбранному муниципальному образованию при условии

```text
overlap_ratio > 0.8
```

5. если условие не выполнялось, объект относился к категории `Не определено`.

При выборе максимального пересечения использовалось разбиение по:

```text
season × id
```

поскольку значения `id` могут повторяться в различных сезонах.

После применения данного правила среди 324 314 анализируемых объектов к категории `Не определено` были отнесены 78 объектов.

## 8. Cold-cache измерения

Для каждой комбинации:

```text
аналитический запрос × модель хранения
```

выполнялось **5 cold-cache измерений**.

Непосредственно перед каждым измерением выполнялась команда:

```sql
SELECT * FROM pg_buffercache_evict_all();
```

Таким образом, перед каждым cold-запуском очищался кэш страниц PostgreSQL `shared buffers`.

Термин **cold-cache** в данном эксперименте относится только к PostgreSQL buffer cache.

Кэш файловой системы Windows и аппаратные уровни кэширования накопителя принудительно не очищались. Поэтому cold-cache результаты не следует интерпретировать как измерения полностью «холодной» системы хранения.

---

## 9. Warm-cache измерения

После завершения серии cold-cache измерений выполнялись:

1. два дополнительных прогревающих запуска;
2. десять измеряемых warm-cache запусков.

Прогревающие выполнения не включались в итоговую статистику.

Между десятью измеряемыми warm-cache запусками очистка PostgreSQL shared buffers не выполнялась.

Таким образом, для каждой комбинации запрос × архитектура сохранялись:

```text
5 cold-cache измерений
10 warm-cache измерений
```

и дополнительно выполнялись два неучитываемых прогревающих запуска.

---

## 10. Статистическая обработка результатов

Для каждой комбинации:

```text
запрос × модель × режим кэширования
```

рассчитывались:

- медиана;
- среднее арифметическое;
- минимальное значение;
- максимальное значение времени выполнения.

Основным показателем при сравнении архитектур принято **медианное время выполнения в warm-cache режиме**.

Медиана использовалась как центральная характеристика серии повторных измерений, менее чувствительная к единичным колебаниям времени выполнения.

Cold-cache результаты сохранялись отдельно и использовались для дополнительной оценки влияния состояния буферного кэша.

---

## 11. Предварительная обработка моделей III и IV

Модели III и IV используют предварительно сформированные аналитические структуры. Поэтому время выполнения аналитического `SELECT` не включает стоимость их первоначального построения.

Эти затраты измерялись отдельно.

### Модель III

Первоначальное построение включало:

- создание `mv_crop_season`;
- создание `mv_municipality_crop_season`;
- создание `mv_land_user_crop_season`;
- создание индексов производных структур.

Медианное время полного первоначального построения модели III составило:

```text
28 251.393 ms
≈ 28.251 s
```

Для модели III также отдельно исследовалось обновление материализованных представлений с помощью `REFRESH MATERIALIZED VIEW`.

### Модель IV

Первоначальное построение включало:

- формирование измерений;
- пространственное отнесение объектов к муниципальным образованиям;
- формирование таблицы фактов;
- создание индексов;
- выполнение `ANALYZE`.

Медианное время полного первоначального построения модели IV составило:

```text
22 137.150 ms
≈ 22.137 s
```

Для модели IV в данном эксперименте измерялось полное первоначальное формирование структуры. Отдельный эксперимент по инкрементальному обновлению таблицы фактов не проводился.

Следовательно, времена выполнения аналитических запросов к моделям III и IV должны рассматриваться совместно с отдельно приведенными затратами на предварительное формирование соответствующих структур.

## 12. Особый статус Z07 и Z08

Сценарии Z07 и Z08 требуют отдельной интерпретации.

### Z07

Для моделей I и II непосредственно во время запроса выполняется пространственное определение территориальной принадлежности объектов.

Для моделей III и IV территориальная принадлежность была рассчитана ранее при формировании производных структур.

Следовательно:

```text
I / II   — пространственное вычисление;
III / IV — чтение предварительно рассчитанного результата.
```

### Z08

Для моделей I и II непосредственно выполняется расчет площади исходных геометрий средствами PostGIS.

Для моделей III и IV геометрия в аналитических структурах отсутствует, а запрос использует ранее рассчитанное значение `area_ha`.

Следовательно:

```text
I / II   — непосредственный расчет площади геометрии;
III / IV — чтение предварительно рассчитанной площади.
```

По этой причине для Z07 и Z08 **не рассчитывается прямой коэффициент ускорения моделей III и IV относительно моделей I и II**.

Времена выполнения этих сценариев приводятся как характеристики соответствующих стадий обработки.

---

## 13. Сравнение с базовой моделью

Для аналитических запросов, допускающих такое сравнение, изменение времени выполнения модели `i` относительно базовой модели I определяется как:

```text
K_i = T_I / T_i
```

где:

- `T_I` — медианное warm-cache время выполнения запроса в модели I;
- `T_i` — медианное warm-cache время выполнения того же аналитического запроса в сравниваемой модели.

При:

```text
K_i > 1
```

время выполнения аналитического запроса меньше, чем в модели I.

При:

```text
K_i < 1
```

время выполнения аналитического запроса больше, чем в модели I.

Для моделей III и IV данный коэффициент характеризует **только аналитическую фазу работы с уже сформированной структурой** и не включает стоимость предварительной обработки.

## 14. Дисковое пространство

Для оценки полного дискового пространства каждой исследуемой архитектуры использовалась функция PostgreSQL:

```sql
pg_total_relation_size(...)
```

При оценке учитывались:

- исходная таблица;
- индексы;
- TOAST;
- материализованные представления;
- таблицы измерений;
- таблица фактов;
- индексы производных структур.

Таким образом, сравнивался полный объем хранения каждой архитектуры, включая исходные данные, а не только объем дополнительных аналитических структур.

---

## 15. Воспроизводимость

Репозиторий содержит:

- определения четырех исследуемых архитектур;
- минимальное описание вспомогательного муниципального слоя;
- SQL-реализации Z01–Z10;
- процедуру автоматизированного измерения производительности;
- агрегированные результаты эксперимента.

Исходные пространственные данные не публикуются.

Поэтому репозиторий обеспечивает воспроизводимость **схемы эксперимента, SQL-логики и методики измерения**, тогда как точное воспроизведение численных результатов требует исходного набора данных, использованного в исследовании.
